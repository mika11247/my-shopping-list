# 退会機能の本番反映判定

## 反映前に管理者が確認する項目

- VercelのProductionとSupabaseのプロジェクトrefを照合する。現行の `/api/delete-user` のFirewall denyとアプリ側の停止を確認する。専用ブランチは `vercel.json` でGit自動デプロイを抑止している。別ブランチを使う場合はpush前にそのブランチも抑止する。本番Supabaseに接続するPreviewを検証に使用しない。
- 2026-11-27の本番メタデータ調査ではPostgreSQL 17.11、実行ロール `postgres`、DBと `extensions` の作成権限、`auth.jwt()` と `auth.sessions.not_after` の存在、Authセッションの参照権限、Vaultの作成関数・参照権限と対象表のSELECT付与権限、Storageポリシーの委譲を確認した。本番では `pg_cron` と `pg_net` が未導入のため、実際の拡張導入、pg_netキューACLの変更、ジョブ登録は承認後の適用ゲートとする。適用に失敗した場合は既存の権限やStorage所有者を緩めずに停止する。
- 暗号化保管先、保全担当、復元担当、書き込み停止方法を用意する。Vercelの退会パス遮断だけでは公開画面、直接Data API、Storage、管理バッチからの通常書き込みは止まらない。保全中は対象の書き込みを調整し、取得前後の件数と画像メタデータを照合する。

## Freeプランでの保全と復元

| 対象 | 保全と復元 | 限界と対応 |
|---|---|---|
| DB | PostgreSQL 17クライアントのnative `pg_dump` のcustom形式を暗号化先に取得する。スキーマ、データ、RLS、関数、トリガー、ACLの対象を `pg_restore --list` と保全前後の件数で照合する。隔離先で対象TOC・依存順を確認し、障害時も必要な差分だけを復元する。 | Freeの手動論理保全は取得時点が境界となる。即時の全体巻き戻しやPITRを前提にしない。読み取り権限フラグだけでダンプの完全性を判断せず、実ダンプの終了コード・対象一覧・隔離復元が揃うまで公開を保留する。 |
| Auth・関連行 | `auth.users`、`auth.identities` と対象のプロフィール・グループ・所属などの関連行を保全対象として照合する。復元の順序はAuthユーザー、本人確認済みの同一プロバイダー識別子、関連行とする。隔離では架空のGoogle subject、Authメタデータ、同一UUID、プロフィール・所有グループ・所属の選択復元を確認した。 | セッション、refresh token、ワンタイムトークン、MFA認証状態は再開用の復元対象から外す。Google OAuthクライアントの設定と秘密鍵は別管理。実Google連携の再開は隔離OAuth試験を通過させる。連携を照合できない場合は本人の承認済み再リンクを行うまで復元アカウントの利用を保留する。 |
| Storage | バケット設定、オブジェクトの元パス・所有者・メタデータと、Storage APIで取得した画像本体・SHA-256を対応付ける。欠損画像だけを復元し、対象UUIDの新規認証セッションによるアップロードで `owner_id`、パス、表示、関連行を照合する。架空アカウントの同一UUID再作成後にこの所有権復元を確認した。 | DBダンプに画像本体は含まれない。管理者アップロードで元所有者が戻るとは扱わない。旧パスや元ユーザーの本人確認を解決できない画像は公開前に復旧可否を決め、所有者情報のSQL書き換えで回避しない。 |
| 運用設定 | Vercelのフラグ・Firewall・Cronのジョブ定義、Google OAuth設定、Resendの送信元、ワーカーシークレットの保管先と再設定手順を記録する。 | 外部サービスの設定やVaultの復号可能性は論理ダンプと別管理。秘密値は既存の安全な保管先から再設定し、必要ならローテーションする。 |

同一UUIDを復元する場合は、旧 `auth.sessions` とrefresh tokenを復元しない。4本のマイグレーションで導入する認可はJWTの `session_id` が現行のAuthセッションに一致することを必要とする。隔離では修正前に旧JWTで復元後の行を読めることを再現し、修正後に個人行の読み取り・書き込み・画像アップロードを拒否し、新規セッションで利用できることを確認した。復元直後のアプリがこのセッション照合を持つ配備であることを必ず照合する。

## 4本の適用と段階検証

1. **保全と事前確認。** 上記の保全を管理者が実施する。対象ref・SHA・実行ロール・外部キー・RLS・Storage参照・My Itemsカウンター不一致件数を記録する。OAuth、Resendの実送信キーの範囲、専用Google利用者と受信箱を用意する。専用Google利用者での実配信試験は隔離Supabase・OAuthクライアントで先に行い、送信元・配信イベント・コード受領・別セッションと期限切れの拒否・完了通知を確認する。
2. **停止状態で適用。** Firewall deny、`ACCOUNT_WITHDRAWAL_INTAKE_DISABLED=true`、APIとUIの機能フラグ停止を維持する。SQLを順にそれぞれのトランザクションで適用する。
   1. `20261127000100_shopping_group_transfer.sql`
   2. `20261127000200_account_withdrawal.sql`（セッション照合を含む）
   3. `20261127000300_account_withdrawal_write_fence.sql`
   4. `20261127000400_account_withdrawal_cron.sql`
3. **適用後確認。** RPCのスキーマ反映とロール、旧ポリシーの維持、追加の3種の制限的Storageポリシー、一般ロールのVault／キュー拒否、Authの旧セッション拒否、既存機能の通常セッション、My Itemsカウンターの一致を確認する。Cron移行SQLがジョブを起動していないことを確認する。保全・権限・確認結果に問題があればここで停止する。
4. **専用アカウントだけを受付。** ワーカーの秘密値とジョブを管理者が設定する。テスト時の通常ユーザー受付は、退会パスを専用テスト元だけに絞るFirewall設定が確認できてから一時的に許可する。Cronの送信元を安全に区別できない場合は、その間ジョブを停止する。専用アカウントの要求が登録されたら、アプリの新規受付を再度停止してから、Cronが到達できる公開済み配備・Firewall設定へ切り替える。受付停止中もワーカー・受付済みステータスは利用できる。無認証workerが拒否され、一般利用者の新規退会が受付停止されることを確認する。
5. **ワーカーと通知を確認してから一般公開。** CronのHTTP応答、退会工程、Auth・画像・共有データの状態、完了通知を確認する。旧配備URLの退会経路も確認する。Firewall・受付制限の一般公開切替は、この確認後に別途行う。

異常時は新規受付を止め、必要ならFirewallを再遮断し、Cronジョブを無効化する。pg_netのキュー、実行中ワーカー、リースを確認してから対応する。適用中のSQLはエラー時にロールバックし、すでにコミットしたものは適用済みとして記録する。既存RLSを緩めたりAuthの旧セッションを戻したりせずに、工程ごとの前方修正または承認済みの差分復元を選ぶ。アプリの切り戻しで削除済みの行や画像は復元できない。
