# My Items: バックアップを取得しない方針での安全検証

本番DBバックアップを今回は取得しない、というユーザーの明示方針を採用。バックアップ取得を実行条件として再要求しない。本番DBの変更、コミット、push、デプロイは未実施。

## 修正内容
- カウンターからauth.users外部キーを除去。Auth不在のMy Itemsとその件数を保持し、初期化時の外部キー違反を解消。
- カウンターはMy Itemsの派生情報。Authの有無だけでは削除しない。残っているMy Itemsと同じUUIDのAuthが復旧すれば、既存件数がそのまま枠を消費する。
- 最後のMy Itemを正常削除して件数が0になったときだけ、そのユーザーの空カウンターを削除。原本が残るAuth不在ユーザーにはカウンターも残る。
- Auth/データ復元後の不一致は管理者用my-items-reconcile.sqlで、元のMy Itemsを変えず再集計する。復元中の書込みを止め、再集計・照合が終わるまで再公開しない。
- 上限超過済みデータは保持。編集と削除は可能、新規登録は上限未満に戻るまで拒否。
- RLS/Storageポリシー、既存セキュリティ関数、退会503 APIは変更しない。
- 登録/削除トリガー・カウンター原子更新による直接INSERT、upsert、bulk、競合防止は維持。

## 時間制限・復旧・残存リスク
- lock_timeout5秒はロック取得待ち、statement_timeout30秒は各SQL文、idle_in_transaction_session_timeout60秒は待機接続の制限。トランザクション全体が30秒以内という保証ではない。ロック保持中はMy Items書込みが待つ。
- COMMIT前のエラーはROLLBACK/切断でトランザクションを終了してロック解放。成功不明時は再実行禁止。
- COMMIT後はSQLのROLLBACKでは戻らない。まず対象書込みを止め、元データは触らず、必要なら再集計またはガードの前方修正を行う。
- 緊急撤去は別途承認後、正しい新規オブジェクトだけであることを検証して実行。撤去すると登録上限のすり抜けが再び可能になる。再適用時には全件数を再集計する。
- バックアップなしでは、COMMIT後の不測の原本変更/削除・画像消失を元へ戻す保証はない。局所撤去は原本の復旧手段ではない。
- 元のMy Itemsが残る限り、その所有者UUIDと件数の派生情報も非公開で残る。Auth削除だけでカウンターを消す設計にはしない。
- 画像本体の内容比較はこのPostgreSQLテストでは扱わない。Storageポリシー/メタデータの不変は検証したが、実Storageサービス全体の互換性保証ではない。
